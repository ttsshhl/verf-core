# VERF core — ядро деплоя

GitHub push → сборка образа → запуск контейнера → домен вида `slug.verf.dev` с автоматическим SSL.

Это MVP-ядро: одна нода, без оркестрации кластера. Рассчитано на один VPS, поднимающий десятки проектов — этого достаточно для первых сотен пользователей.

## Что уже работает (покрыто тестами)

- Проверка подписи GitHub-вебхука (HMAC-SHA256) — 6 тестов
- Клонирование/обновление репозитория, определение типа проекта (Node / Python / статика / свой Dockerfile), автогенерация Dockerfile — 9 тестов
- REST API деплоя: создание/список/удаление проектов (админ-доступ), приём вебхука, история деплоев — 9 тестов
- Полный пайплайн деплоя, включая обработку ошибок и запись логов в БД
- **Авторизация**: хеширование паролей (bcrypt), выдача и проверка JWT-токенов — 8 тестов
- **Личный кабинет**: регистрация/вход, привязка проектов к владельцу, лимиты по тарифам (free/pro/business), изоляция чужих проектов — 12 тестов
- **Биллинг (ЮKassa)**: создание платежа, вебхук с перепроверкой статуса напрямую у ЮKassa (тело вебхука не считается источником истины — это защита от подделанных запросов) — 8 тестов
- **Биллинг криптой (Cryptomus)**: создание инвойса, проверка подписи вебхука (MD5 от тела + API-ключ — это документированная схема Cryptomus, подпись покрывает весь платёж целиком, так что подмена одного поля, например статуса, инвалидирует подпись) — 12 тестов

Docker-слой (`app/deployer.py`) написан на официальном `docker` SDK и рассчитан на реальный Docker-демон — у меня в песочнице его нет физически, поэтому этот файл не покрыт тестами напрямую, но весь пайплайн до и после него — да. Реальные вызовы к ЮKassa (`app/billing.py`) в тестах замоканы по той же причине — сеть до api.yookassa.ru недоступна из песочницы, но сама бизнес-логика (создание/активация подписки, лимиты, защита от подделки вебхука) протестирована полностью.

```
pytest tests/ -v    # 177 passed
```

## API личного кабинета

```
POST /auth/register        {"email", "password"}           → {"access_token"}
POST /auth/login           {"email", "password"}           → {"access_token"}
GET  /me                   (Authorization: Bearer <token>) → {"id", "email", "plan"}

POST   /me/projects        создать свой проект (с проверкой лимита тарифа) — repo_url, repo_full_name или ни того, ни другого (CLI/ZIP-проект)
GET    /me/projects        список только своих проектов
DELETE /me/projects/{slug} удалить свой проект

POST /me/projects/{slug}/deploy   ZIP-архив (multipart) → задеплоить без git — путь для CLI и загрузки в кабинете
GET  /me/deployments/{id}         статус + лог одного деплоя — для опроса прогресса из CLI

POST   /me/projects/{slug}/domain  {"domain": "example.com"} → привязать свой домен к проекту
DELETE /me/projects/{slug}/domain  отвязать домен

PUT /me/projects/{slug}/env  {"env": {"KEY": "value", ...}} → заменить переменные окружения проекта целиком

GET /me/projects/{slug}/logs?lines=200  → последние строки stdout/stderr работающего контейнера (не билд-лог деплоя — именно живые логи, включая падения после старта)

POST /billing/subscribe    {"plan": "pro"|"business", "provider": "yookassa"|"cryptomus"} → ссылка на оплату
POST /webhook/yookassa     (вызывается самой ЮKassa)        → активирует подписку после реальной проверки платежа
POST /webhook/cryptomus    (вызывается самой Cryptomus)     → активирует подписку после проверки подписи
```

`provider` необязателен, по умолчанию `"yookassa"` — существующие интеграции с картой продолжат работать без изменений на фронте, крипта — просто ещё один вариант оплаты того же тарифа.

## Свои домены (custom domains)

Каждый проект живёт на `{slug}.verfdeploy.ru` автоматически. Пользователь может дополнительно привязать свой собственный домен — но SSL для чужого домена работает иначе, чем для наших поддоменов, и это стоит понимать перед тем, как трогать эту часть кода:

- **`{slug}.verfdeploy.ru`** — сертификат через DNS-01 (у нас есть API-доступ к reg.ru, поэтому мы можем сами создать `_acme-challenge` TXT-запись). С недавних пор это **wildcard**-сертификат на `*.verfdeploy.ru`, получается один раз и переиспользуется для всех проектов — см. `app/deployer.py::_labels()`.
- **Домен пользователя** (`example.com`) — DNS-01 здесь невозможен, у нас нет доступа к его регистратору. Вместо этого — **HTTP-01** через отдельный резолвер `http` в `docker-compose.yml` (задействует порт 80, поэтому глобальный редирект `web → websecure` в Traefik намеренно **не включён** — иначе ACME-челлендж на 80 порту сам себя ломал бы, мы уже проходили это с основным доменом). HTTP-01 — это по факту и есть проверка владения: сертификат выпустится только если DNS домена реально указывает на наш сервер.

Пользователю нужно направить домен через **CNAME на `{slug}.verfdeploy.ru`**, а не A-запись на IP напрямую — специально, чтобы домен пережил очередную смену IP сервера (за эту сессию IP менялся трижды из-за блокировок магистральными провайдерами; CNAME на наш поддомен избавляет пользователей от необходимости что-либо менять при следующей смене).

При привязке домена (`POST /me/projects/{slug}/domain`) бэкенд best-effort пересоздаёт контейнер сразу же (если он уже запущен), не дожидаясь следующего деплоя — см. `_redeploy_running_container()` в `app/main.py`. Тот же хелпер используется и для обновления переменных окружения (`PUT /me/projects/{slug}/env`) — он просто перечитывает текущее состояние проекта (env, домен, тариф) и пересоздаёт контейнер с этим состоянием, так что оба изменения применяются одинаково. Если Docker недоступен в момент запроса — изменение всё равно сохраняется в базе и применится при следующем реальном деплое.

**Билд-лог деплоя** (`Deployment.log`, видно в истории деплоев в кабинете) и **живые логи контейнера** (`GET /me/projects/{slug}/logs`) — разные вещи. Первый фиксирует только последовательность клонирование→сборка→запуск и обрывается в момент, когда контейнер поднялся — упавший после старта бот (например, из-за `KeyError` на отсутствующей переменной окружения) в билд-логе будет выглядеть как `running`, хотя процесс внутри уже упал и перезапускается по кругу. Именно для таких случаев нужны живые логи — `container.logs()` через Docker SDK, которые показывают, что реально происходит с процессом прямо сейчас.

## Гибкий входной файл Python-проектов

Когда пользователь **не** приносит свой `Dockerfile`, платформа генерирует его сама и раньше жёстко запускала `python main.py`. Теперь `app/builder.py::_detect_python_entrypoint()` ищет по порядку `main.py → bot.py → app.py → run.py → __main__.py` и берёт первый найденный — так шаблоны ботов с `bot.py` (частая история со скачанными откуда-то заготовками) заводятся без переименования файлов. `main.py` всегда в приоритете, если есть несколько подходящих файлов.

Если в архиве уже **есть свой** `Dockerfile` — платформа его не трогает и использует как есть (это было и раньше, не новое поведение) — учитывай, что если такой сторонний `Dockerfile` сам ссылается на неверное имя файла, это не то, что мы можем починить автоматически: слишком похоже на настоящий чужой Dockerfile для угадывания.

## Telegram Bot API — фикс сетевой нестабильности

Часть IP-адресов `api.telegram.org` нестабильно маршрутизируется с этого хостинга (проверено вручную несколько раз — какие именно адреса «плохие», от раза к разу отличается). Вместо того чтобы просить каждого автора бота патчить свой код через `/etc/hosts`, платформа сама прописывает рабочий адрес **каждому** контейнеру через `extra_hosts` Docker (`app/deployer.py::run_container()`, см. `TELEGRAM_API_PINNED_IP` в `app/config.py`) — бесплатно и без побочных эффектов для проектов, которые вообще не обращаются к Telegram.

Если этот конкретный IP тоже когда-нибудь перестанет быть надёжным — правится одной строкой в `.env` (`VERF_TELEGRAM_API_PINNED_IP=...`), без изменений кода.

## CLI (`cli/verf.py`)

Деплой без GitHub вообще — ноль зависимостей, только стандартная библиотека Python. Пользователь просто скачивает файл и запускает:

```
python3 verf.py login              # почта + пароль, токен сохраняется в ~/.verf/config.json
python3 verf.py create my-bot --kind bot
cd my-bot/
python3 verf.py deploy my-bot      # архивирует текущую папку, грузит на сервер, стримит лог сборки
python3 verf.py projects           # список своих проектов
```

Архивация сама исключает `.git`, `node_modules`, `venv`, `__pycache__` и подобное (список — `DEFAULT_IGNORE_DIRS` в файле). `deploy` заливает ZIP на `POST /me/projects/{slug}/deploy` и опрашивает `GET /me/deployments/{id}` каждые 2 секунды, печатая новые строки лога по мере появления — тот же паттерн, что у `railway up`/`flyctl deploy`.

Проверено вручную end-to-end на реальном локальном сервере (не только юнит-тестами): регистрация → создание проекта → архивация с корректным исключением `.git`/`node_modules` → загрузка → построчный стриминг лога сборки до места, где не хватает Docker (в тестовом окружении) — на самом сервере, где Docker есть, доходит до конца.

Тот же путь (`POST /me/projects/{slug}/deploy`) использует и кабинет — вкладка «ZIP-архив» при создании проекта делает ровно то же самое через `fetch()` вместо `urllib`.

Лимиты тарифов сейчас в коде (`app/config.py`): `PLAN_PROJECT_LIMITS` — free: 1 проект, pro: 5, business: без лимита. `PLAN_MEM_LIMITS` / `PLAN_CPU_QUOTAS` — реальные лимиты Docker-контейнера на проект (free: 512 МБ / 0.5 vCPU, pro: 2 ГБ / 1 vCPU, business: 8 ГБ / 2 vCPU), применяются в `pipeline.py` по фактическому тарифу владельца проекта на каждом деплое — не только заявлены на сайте, но и реально ограничивают контейнер через `docker run --memory --cpu-quota`.

Цены (`PLAN_PRICES_RUB`) — стартовые: 490₽ (pro) и 1 990₽ (business) вместо изначально задуманных 990₽/2 990₽. Смысл: инфраструктура стоит копейки относительно этих цифр (см. разбор маржинальности выше в истории проекта), а на старте важнее набрать первых платящих пользователей и обратную связь, чем максимизировать цену за клиента. Цены — просто две константы в `config.py`, поднять их для новых подписчиков в любой момент — значит поменять две цифры и задеплоить; действующие подписки при этом не пересматриваются (см. `oferta.html`, п. 5.1).

Старые эндпоинты `/projects` (админские, по `X-API-Key`) никуда не делись — это ручной доступ для тебя как владельца платформы, отдельно от самостоятельной регистрации пользователей.

## Подключение GitHub (автосоздание вебхуков)

Без этого пользователи всё ещё могут вставлять URL репозитория вручную и настраивать вебхук самостоятельно — но с подключённым OAuth App личный кабинет показывает список репозиториев и сам создаёт вебхук при создании проекта.

1. Зайди на [github.com/settings/developers](https://github.com/settings/developers) → **OAuth Apps → New OAuth App**
2. Заполни:
   - **Application name**: `VERF` (или что угодно)
   - **Homepage URL**: `https://verfdeploy.ru`
   - **Authorization callback URL**: `https://api.verfdeploy.ru/auth/github/callback` — должно совпадать с `VERF_GITHUB_REDIRECT_URI` в точности, иначе GitHub откажет в обмене кода
3. После создания возьми `Client ID`, затем нажми **Generate a new client secret** и возьми `Client Secret` (показывается один раз)
4. Впиши в `.env`:
   ```
   VERF_GITHUB_CLIENT_ID=...
   VERF_GITHUB_CLIENT_SECRET=...
   ```
5. `docker compose up -d` — переменные подхватятся при пересоздании контейнера

Без этих двух переменных кнопка «Подключить GitHub» в кабинете вернёт понятную ошибку (502 с объяснением), остальной кабинет продолжит работать как раньше.

**Как это работает:** пользователь жмёт «Подключить GitHub» → кабинет запрашивает одноразовый nonce у бэкенда (обычный authenticated-запрос) → браузер переходит по ссылке с этим nonce → бэкенд меняет его на короткоживущий JWT с типом `github_connect` и редиректит на GitHub → пользователь подтверждает доступ → GitHub возвращает `code` на callback → бэкенд меняет `code` на access-токен через API GitHub, сохраняет его на пользователе. Токен пользователя нигде не попадает в URL или в логи сервера — только одноразовый nonce и подписанный JWT-стейт, оба короткоживущие и бесполезные при повторном использовании.

При создании проекта через список репозиториев (`repo_full_name` вместо `repo_url`) бэкенд сам создаёт push-вебхук у GitHub через API — это best-effort: если не получилось (например, токену не хватает прав на конкретный репозиторий), проект всё равно создаётся, просто `webhook_auto_configured` останется `false`, и в кабинете будет показана обычная инструкция для ручной настройки.

## Настройка почтовых уведомлений

Письмо на почту отправляется в двух случаях: при регистрации (приветственное) и при успешной оплате тарифа (подтверждение). Оба — best-effort через `BackgroundTasks`: если SMTP не настроен или временно недоступен, это никогда не ломает саму регистрацию или активацию подписки — просто письмо не уйдёт, ошибка проглатывается в `_send_email_best_effort()` (`app/main.py`).

По умолчанию настроено на Yandex Mail (`smtp.yandex.ru:465`), раз бизнес уже использует `fixakk@yandex.ru`:

1. Зайди в веб-версию Яндекс Почты → **Настройки → Пароли приложений**
2. Создай новый пароль приложения для **«Почта» / SMTP** (не аккаунтный пароль — он не подойдёт, Яндекс требует именно отдельный пароль приложения для SMTP/IMAP-доступа)
3. Впиши в `.env`:
   ```
   VERF_SMTP_USER=fixakk@yandex.ru
   VERF_SMTP_PASSWORD=<пароль приложения>
   ```
4. `docker compose up -d` — переменные подхватятся при пересоздании контейнера

Без `VERF_SMTP_USER`/`VERF_SMTP_PASSWORD` письма просто не отправляются (тихо, без ошибок наружу) — остальной кабинет продолжает работать как обычно.

Шаблоны писем — в `app/notifications.py` (`send_welcome_email`, `send_payment_confirmation_email`), простой inline-HTML в стиле остального продукта, без внешних зависимостей на шаблонизатор.

## Настройка биллинга

1. Зарегистрируй магазин на yookassa.ru, пройди верификацию (нужно для приёма платежей в РФ)
2. В личном кабинете ЮKassa возьми `shopId` и `secretKey` (Настройки → Магазины → API)
3. Впиши их в `.env` как `VERF_YOOKASSA_SHOP_ID` и `VERF_YOOKASSA_SECRET_KEY`
4. В настройках магазина ЮKassa укажи URL для уведомлений: `https://api.твой-домен/webhook/yookassa`

Без этих переменных всё остальное (регистрация, вход, лимиты, личный кабинет) работает — сломается только сама оплата.

## Настройка оплаты криптой (Cryptomus)

1. Зарегистрируйся на cryptomus.com, создай проект/магазин
2. В настройках проекта возьми `Merchant ID` и `Payment API Key`
3. Впиши в `.env` как `VERF_CRYPTOMUS_MERCHANT_ID` и `VERF_CRYPTOMUS_API_KEY`
4. В настройках проекта укажи URL для колбэков: `https://api.твой-домен/webhook/cryptomus`

Цены для крипто-оплаты заданы в `app/config.py` (`PLAN_PRICES_USD`) как примерная фиксированная привязка к рублёвым тарифам по курсу ~80₽/$ — это не live-курс, поэтому если рубль сильно качнётся, стоит поправить цифры вручную (или в будущем подключить получение курса в реальном времени).

**Важный юридический нюанс**: приём криптоплатежей как средства оплаты товаров/услуг между резидентами РФ — юридически неоднозначная область (регулирование цифровых финансовых активов в целом не поощряет использование крипты как платёжного средства внутри страны). Это не значит, что так делать нельзя — многие небольшие проекты в РФ/СНГ используют подобные шлюзы, оформляя это как расчёты с иностранным контрагентом, поскольку сам Cryptomus — не российская компания. Но это не полностью чистая с точки зрения буквы закона схема, и однозначного публичного разъяснения по такому конкретному случаю (SaaS-подписка, оплаченная в крипте) нет. Раз я не юрист, тут стоит либо свериться со знающим человеком, либо принять этот риск осознанно.

## Архитектура

```
GitHub push
     │
     ▼
POST /webhook/github/{slug}   ── проверка HMAC-подписи (app/webhook.py)
     │
     ▼
Deployment(status=pending) записан в БД
     │  (ответ GitHub'у уходит сразу — сборка идёт в фоне)
     ▼
app/pipeline.py: run_deploy()
     │
     ├─ builder.clone_or_pull()      git clone/pull, возвращает commit SHA
     ├─ builder.detect_profile()     ищет Dockerfile → package.json → requirements.txt → index.html
     ├─ builder.ensure_dockerfile()  генерирует Dockerfile, если репозиторий пришёл без него
     ├─ deployer.build_image()       docker build
     └─ deployer.run_container()     останавливает старый контейнер, запускает новый с лейблами Traefik
```

Traefik читает Docker-лейблы каждого запущенного контейнера и сам настраивает роутинг + SSL — в `app/deployer.py` ничего вручную не прописывается.

## Запуск на VPS (Timeweb Cloud / Selectel / любой с Ubuntu 22.04+)

1. **Установить Docker и Docker Compose**
   ```bash
   curl -fsSL https://get.docker.com | sh
   ```

2. **Направить домен на сервер** — A-запись `*.verf.dev` (или твой домен) → IP VPS. Wildcard-запись нужна, чтобы `любой-slug.verf.dev` резолвился без ручной настройки DNS под каждый проект.

3. **Склонировать этот репозиторий на сервер и настроить `.env`**
   ```bash
   cp .env.example .env
   # заполнить ACME_EMAIL, VERF_DOMAIN_SUFFIX, VERF_ADMIN_API_KEY
   ```

4. **Поднять стек**
   ```bash
   docker network create verf-net || true
   docker compose up -d --build
   ```

5. **Проверить, что ядро живо**
   ```bash
   curl http://127.0.0.1:8000/health
   # {"status": "ok"}
   ```

## Как задеплоить первый проект

1. **Зарегистрировать проект** (с VPS или через SSH-туннель на порт 8000, т.к. `/projects` не публичный):
   ```bash
   curl -X POST http://127.0.0.1:8000/projects \
     -H "X-API-Key: $VERF_ADMIN_API_KEY" \
     -H "Content-Type: application/json" \
     -d '{
       "slug": "my-bot",
       "repo_url": "https://github.com/you/my-bot.git",
       "branch": "main",
       "kind": "bot"
     }'
   ```
   В ответе будет `webhook_secret` — он нужен на следующем шаге.

2. **Добавить вебхук в GitHub** (Settings → Webhooks → Add webhook):
   - Payload URL: `https://твой-домен/webhook/github/my-bot` *(проксируется через Traefik — добавь лейблы на verf-core в compose, если хочешь публичный доступ к вебхуку без открытого порта 8000; в MVP-конфиге вебхук пока идёт напрямую на 8000, см. "Известные ограничения")*
   - Content type: `application/json`
   - Secret: значение `webhook_secret` из шага 1
   - Событие: `Just the push event`

3. **Пушнуть в репозиторий** — GitHub дёрнет вебхук, VERF соберёт образ и поднимет контейнер на `https://my-bot.verf.dev`.

4. **Проверить статус деплоя**
   ```bash
   curl http://127.0.0.1:8000/projects/my-bot/deployments \
     -H "X-API-Key: $VERF_ADMIN_API_KEY"
   ```

## Известные ограничения MVP (осознанно, чтобы не блокировать запуск)

- **Порт 8000 не публикуется через Traefik по умолчанию.** Для приёма вебхуков GitHub тебе нужен публичный HTTPS-адрес — либо добавь Traefik-лейблы на сервис `verf-core` в `docker-compose.yml` (аналогично тому, что `deployer.py` делает для пользовательских контейнеров), либо на первое время используй `ngrok`/SSH-туннель для теста.
- **Один VPS, без очереди задач.** Деплой идёт в `BackgroundTasks` внутри процесса FastAPI — нормально для десятков проектов, но если одновременных пушей станет много, следующий шаг — вынести `run_deploy` в Celery/RQ с отдельным воркером.
- **SQLite.** Хватает для одного узла. Переезд на Postgres — это просто смена `VERF_DATABASE_URL`, код не завязан на конкретную БД.
- **Нет личного кабинета и биллинга** — это следующий кусок в очереди, ты сам так решил на предыдущем шаге.
